# v0.8.0 사용자 확인 체크리스트

## 상태·진행 원칙

2026-10-03 KST **준비 문서 / 사용자 UAT NOT RUN**이다.
[릴리스 런북](./RELEASE_V0.8.0.md)의 운영 DB·API/scheduler 배포와 안전한 smoke가 끝난 뒤 사용한다.
현재 운영 화면은 [객실관리 앱](https://room-management-system-prod.vercel.app/)이다.
프런트 담당자가 새 API를 아직 연결하지 않은 기능은 API 배포 성공과 화면 완료를 구분한다.

- 관리자·메이드는 각자 정상 계정으로 본인 업무 범위만 확인한다. 확인을 위해 계정을 새로 만들거나 타인의 로그인 정보를 공유하지 않는다.
- 먼저 조회만 한다. 생성·취소·시작·완료·신고·검수·송금 표시는 **실제 필요한 업무를 사용자가 선택한 경우에만** 실행한다. 테스트를 위한 가짜 예약/청소/검수/금전 기록을 만들지 않는다.
- 진행 중 업무를 취소/재배정하거나 계정을 비활성화해서 시험하지 않는다. 일자·DB·Auth 설정·기기 시각을 바꿔 경과 조건을 만들지 않는다.
- 실제 도어락 PIN 변경·bootstrap·물리 확인과 은행 이체/PAID 시험은 제외한다. PIN 조회는 정상 업무에 필요할 때만 하며 원문을 기록하지 않는다.
- 결과는 `PASS`(실제 기대 동작 확인), `FAIL`(실제 불일치), `BLOCKED`(프런트 연결/환경 전제 부족), `NOT RUN`(미실행/데이터 없음)으로 구분한다. 데이터가 없거나 버튼이 없어 확인하지 못한 항목을 PASS로 바꾸지 않는다.

## 2. 프런트 연결 후 확인할 새 계약

현재 공개HTML은 아래 신규 계약을 소비하지 않는다. 상태는 **BLOCKED — 프런트 연결 대기**이며,
운영 API 배포만으로 UAT PASS를 선언하지 않는다. 프런트 담당이 연결한 뒤 아래 확인을 진행한다.

| 기능 | 연결 후 완료 기준 | 초기 결과 |
|---|---|---|
| 배정 근거·취소 표시 #326 | 원 snapshot의 타입/요금·등록 근거·원/유효일을 표시한다. 0원과 unknown을 구분하고 날짜 차이를 이월 근거로 추정하지 않는다. `canCancel`은 advisory이며 실제 명령 오류를 안전하게 처리한다 | BLOCKED |
| 계획/실제 퇴실 #328 | 계획·최초 통보 snapshot과 현재 실제 퇴실을 구분한다. 내일 계획을 실제 퇴실로 표시하지 않으며 과거 이력에 현재 예약/담당을 섞지 않는다 | BLOCKED |
| 미퇴실 사건 목록 #327 | 관리자는 open 목록에서 선택 후 최신 상세 version/fingerprint로 기존 결정을 한다. 목록의 오래된 값으로 확정하지 않는다. 해당 사건 없는 경우 빈 목록은 정상이며 결정 테스트는 NOT RUN이다 | BLOCKED |
| 주급 조정 version #325 | 최신 adjustment-book version으로 기존 정정/취소를 연결한다. 경합409 때 새로 조회하고 사용자 의도를 다시 확인한다. 조회만으로 조정 원장을 만들지 않는다 | BLOCKED |
| 객실별 주급 상세 #324 | 확정 earnings와 미확정 workflow를 구분한다. 무급 재청소/반려 이력은 금전 기여0으로 표시하고 실제 보상은 typed earning 근거를 사용한다. item 포함을 지급 완료로 오해하지 않는다 | BLOCKED |
| 상세 페이지 이동 #324 | 같은 조회 시점의 모든 페이지 기여 합계를 기존 summary와 비교한다. 페이지 사이 상태 변경은 첫 페이지부터 갱신하며 다른 시각/stream 결과를 임의 합산하지 않는다. 영구 동결 snapshot을 기대하지 않는다 | BLOCKED |
| 송금 표시 #331 | 별도 marked와 실제 지급 status를 구분한다. 실제 업무에 필요한 새 on은 종료 KST 주차·양수 근거만 가능하다. 금액 근거 변경 때 on을 유지하며 재확인 필요를 표시하고 별도 재확인을 기록한다. off는 이체 취소/환불이 아니다 | BLOCKED |
| 취소 버튼 ID/CAS #348/#326 | 수동 target의 `cleaningTargetId`/`targetId`, `targetAssignmentVersion`을 요청에 연결한다. 현재 FE 별칭 `manualCleaningRequestId`/`targetVersion` 변환 gap을 해결한다. assignment ID나 메이드 revision을 target CAS로 쓰지 않는다 | BLOCKED |

수동 취소는 명령 자체와 배정 행 버튼을 나눠 확인한다. 정상 연결된 기존 취소 경로가 있고 **실제로 취소해야 하는**
수동 추가/연박 업무만 사용자가 취소한다. 미배정·draft·통보 후 미착수는 가능하며 PIN 조회는 제한이 아니다.
자동 퇴실 청소와 실제 착수/현장 완료/제출/검수 단계는 일반 취소 대상이 아니다.
취소 후 당시 current notified 담당에게만 회수 알림이 보이고 해당 배정의 이후 PIN 접근이 종료되어야 한다.
확인을 위해 먼저 PIN을 열거나 실제 업무를 시작했다가 취소하는 시험은 하지 않는다.

## 3. 확인 기준 artifact와 증거 남기기

준비 시 scoped FE 기준은 dev `09ed28446a4fd43919cddb29ebe442b848548ab8`,
main `d509b44b1371f25d73891e04d355b0cb0e923f5f`다.
공개HTML 1,842,858 bytes / blob `0d4c5e301d559c43eafcfb3c8af32802cfde5140` /
SHA-256 `6f45a263cf9997e7a42db3a54d5e4cf14aa764a25acfe9e3995b4849f47836a3`의
정적 parity만 확인했다. 이 값은 API/실제 화면/사람 UAT PASS 증거가 아니다.
실제 진행 때 배포 API source·Function version과 새 FE artifact를 다시 기록한다.

실패 보고에는 아래 최소 정보만 남긴다.

- 체크 항목, 역할(admin/maid), KST 시각, 화면/버튼 이름, 기대 결과와 실제 결과.
- 안전한 오류 code·HTTP status·문의/request ID, 새로고침 후 같은지 여부. token이 담긴 요청 전문이나 HAR를 붙이지 않는다.
- PIN 원문·고객명/연락처·직원 개인정보·Authorization/refresh token·사진 원문·provider locator·key는 제외한다. 캡처가 필요하면 민감 부분을 제거하며 PIN 표시 화면 원문은 캡처하지 않는다.
