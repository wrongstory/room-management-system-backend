## 결론

원본의 중심은 관리자·메이드 업무를 검증하는 단일 HTML 고충실도 와이어프레임입니다. 현재 `main`은 인증·계정·개발자 상태·가능일·예약·객실의 운영 API subset을 연결했지만, 청소 배정·사진·검수·주급·신규 PIN·Web Push는 여전히 미소비 또는 데모다. 따라서 화면 객체와 fixture를 DB/API 정본으로 옮기지 않는다.

따라서 HTML의 현재 객체 구조를 그대로 DB 테이블로 옮기면 안 됩니다. 화면의 복합 상태를 예약, 점유, 청소 대상, 담당 revision, 수행 회차, 업로드, 제출 버전, 검수, 수익, 지급, 알림, 감사 이벤트로 분리해야 합니다.

## 백엔드가 반드시 보장할 규칙

- 동일 객실의 활성 예약은 `[check-in, check-out)` 반개구간으로 겹치지 않습니다.
- 동일 객실의 활성 청소 대상은 중복 생성되지 않습니다.
- 동일 청소 대상의 현재 담당은 한 명이며 담당 revision을 보존합니다.
- 한 메이드는 여러 업무를 가질 수 있지만 `청소 중` 수행 회차는 한 건뿐입니다.
- 작업 생성 시 객실 타입·단가·템플릿·예약 일정을 스냅샷으로 고정합니다.
- 제출은 client UUID로 멱등 처리하고, 현재 제출 버전만 한 번 승인/반려할 수 있습니다.
- 폭탄방 승인과 전체 청소 승인이 모두 있어야 해당 한 객실의 요금만 정확히 2배가 됩니다.
- `(maid_id, week_start)` 지급 레코드는 한 건이며 `OPEN → PAYING → CHECK/PAID`를 CAS로 전이합니다.
- 과거 기록을 덮어쓰지 않고 정정 이벤트를 추가합니다.
- 고객명, 전화번호, 객실 PIN, 사진은 각각 별도 보존·노출 정책을 적용합니다.

## 발견한 정책 주의점

- `DOCS/17`은 예정 전 `지금 체크아웃`을 요구하고 최신 README는 예약 시각 기반 자동 체크아웃을 설명합니다. 서버는 둘을 양립시켜 예정 시각에는 자동 종료하고, 그 전에는 관리자 수동 종료를 허용하는 모델로 설계했습니다.
- 객실 카드 주 상태 우선순위는 문서 사이 표현 차이가 있습니다. DB에는 색/주 상태를 저장하지 않고 원본 축만 보존하여, 최종 UI 정책이 확정되면 파생 함수만 바꿀 수 있게 했습니다.
- 인증 아이디는 이름형 문자열이지만 Supabase Auth의 password 로그인 식별자는 이메일/전화입니다. 서버가 로그인 아이디를 불변 Auth 사용자 ID에 매핑하고 내부 비공개 이메일을 계산해 로그인합니다. 내부 이메일은 API 응답에 노출하지 않습니다.
