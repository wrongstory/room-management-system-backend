# 장기투숙 SQL 테스트의 KST 경계 검증 (#279)

`reservation_long_stay.sql`은 테스트 transaction마다 한 기준 시각을 고정한다.
기본값은 기존 실패를 재현했던 자정 직후인 2026-09-24 00:04 KST다.
서비스 날짜, 예약/실제 입실, 접근 창, 담당 통보, 회차 활성화·시작,
scheduler와 수동 checkout의 업무 시각은 이 값에서 파생한다.

접근 시작은 같은 KST 날짜의 00:00보다 이르지 않게 하고, 마감은 다음
00:00을 넘기지 않는다. 따라서 기준 시각은 항상 접근 창 안에 있으며,
서비스 날짜와 접근 시작 날짜가 다르지 않다. 이는 테스트 데이터 구성
규칙이며 제품의 접근 창·예약·권한 정책을 변경하지 않는다.

공개 객실 이동 preview는 자체 서버 시각보다 미래인 값을 요구하므로
해당 요청의 effectiveAt만 statement_timestamp() + 1시간을 사용한다.
이 값은 청소 서비스 날짜나 수행 시각의 입력으로 사용하지 않는다.

## 실행

로컬 Supabase를 준비하고 최신 migration을 적용한 뒤 실행한다.

```sh
npm run db:verify
npm run db:test
npm run db:test:long-stay-clock
```

마지막 명령은 23:59:59, 00:00:00, 00:04:00, 00:05:00, 12:00:00 KST의
5개 시각 각각에서 전체 장기투숙 SQL 시나리오 29개 검사를 수행한다.
각 실행은 fixture를 rollback하며 공개 요청 생성, 배정 근거, 회차
활성화·시작, scheduler의 자동 퇴실 방지, 수동 퇴실을 실제 DB에서 검증한다.
CI의 migration job에도 같은 명령을 포함한다.

기준 시각 주입은 테스트 SQL이 읽는 세션 설정과 임시 테이블에만 존재한다.
운영 함수나 서버 clock을 교체하지 않으며 원격 DB URL 입력도 받지 않는다.
psql 성공 종료만으로 통과시키지 않고 TAP plan·번호·성공 개수와 실패를 검사한다.
기존 27개 검사를 유지하고 날짜/실행 창 불변식 2개를 추가했다.
